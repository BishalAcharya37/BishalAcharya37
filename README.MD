### RestroPOS — Multi-Outlet Restaurant SaaS &nbsp; (Backend + Real-Time + Hardware Integration)

![Node.js](https://img.shields.io/badge/Node.js-339933?style=flat&logo=nodedotjs&logoColor=white)

![ESC/POS](https://img.shields.io/badge/ESC%2FPOS-thermal%20printing-6B7280?style=flat)

A real, currently-live client project for a restaurant group running 4 outlets — built solo, backend and hardware integration both, for **PravidhiDigitalInnovation**. This isn't a toy CRUD demo. It covers real restaurant operations end to end: multi-outlet management, floor/table layout, reservations, QR-based guest ordering, live kitchen ticket printing on physical hardware, and billing.

**How it actually works, start to finish**

1. **Guest scans a QR code on the table.** Each table has its own QR code. Scanning it opens a table session, verified against GPS radius so a guest can't fake being at a table they're not physically near. If the table already has guests ordering, a new scan joins the *same* session instead of creating a duplicate one, so everyone at the table lands on one shared bill.
2. **Guest browses the menu and places an order.** Items, variants (Large/Medium/Small), and add-ons are pulled live, filtered to only what's currently available. The cart lives on the frontend — nothing touches the database until the order is placed. Every order carries an idempotency key, so a flaky connection or a double-tap can't create two orders by accident.
3. **The kitchen ticket prints itself — instantly, on a real printer.** The moment an order is placed, the backend fires a `KOT_PRINT_REQUESTED` event over a socket connection. A small local agent app, running on the PC physically wired to the outlet's thermal printer, picks it up and prints a kitchen ticket in under a second. No manual "check the screen and copy the order" step.
4. **Kitchen tracks each item independently.** Every item moves through its own status — Placed → Preparing → Ready → Served — independently of the rest of the order. Tea can be ready while the momo is still cooking, on the same ticket. Once an item hits Preparing, the guest can no longer cancel it.
5. **Staff generates the bill and takes payment.** One or more orders from the same table session combine into a single bill. Payments can be split across multiple methods (Cash, Card, eSewa, Khalti, FonePay, Bank Transfer), with partial payments tracked until the balance clears. The moment a bill is fully paid, the table session auto-closes and a full itemized receipt prints automatically on the same hardware — no second machine needed.

Every step above (table status, new orders, kitchen updates, bill events) also pushes live over Socket.IO to staff devices, so the floor status screen and kitchen queue update in real time without anyone refreshing a page.

**What I built**

- **Multi-outlet foundation** — one organization, many outlets, each with its own floors, tables, halls, staff, and billing profile, architected to scale into a true multi-tenant SaaS without a rewrite. Role-based access (owner, manager, store keeper, finance, viewer, cashier) with per-outlet access scoping.
- **Auth & sessions** — JWT access tokens + rotating refresh tokens with reuse detection (a replayed stolen token kills every session for that user). Guest ordering uses a separate, stateless customer-session token scoped to one table session, checked live against the session's actual status on every use.
- **Real-time layer** — Socket.IO with role- and session-scoped rooms: staff join their outlet's room, guests join their table session's room, nobody sees events outside their own scope. Every state change is a typed event, not a raw string.
- **Order & kitchen workflow** — full lifecycle from placement to per-item kitchen status to serving, with concurrency handled through simple conditional database updates (no distributed locks needed) plus idempotency keys for safe retries. QR ordering includes anomaly protection: GPS-radius checks on every order, live staff visibility as orders come in, and a staff-confirmation gate designed to sit in front of guest orders before they hit the kitchen.
- **Billing** — combines multiple orders into one bill, supports split/partial payments, blocks overpayment, auto-closes the table on full settlement. Optional PAN/VAT detail resolved per-outlet with an org-level fallback, snapshotted onto the bill so historical records stay accurate even if outlet billing info changes later.
- **Hardware integration — kitchen ticket & receipt printing.** Built a separate local Node.js "print agent" that runs on the PC physically connected to each outlet's printer — the same architectural pattern Petpooja, Zomato, and Toast use for kitchen printing, since a cloud-hosted backend has no way to talk directly to a USB printer sitting inside a restaurant. Talks to a **ZKTeco ZKP8005v 80mm thermal printer** over USB, shared through Windows as a network printer, using raw ESC/POS commands via `node-thermal-printer`. Logs in through the backend's normal login endpoint with its own low-privilege account (no special backend code path) and self-schedules its own token refresh by decoding the JWT's expiry client-side. Tried two other approaches before landing on the working one (a native printer driver needing per-machine compilation, and Windows' built-in print command, which doesn't work with modern Plug-and-Play USB POS printers). Found and fixed a bug where the print buffer wasn't cleared between jobs, silently reprinting every previous order's ticket on top of each new one. Kitchen tickets are deliberately stripped down (item, variant, add-ons, notes, parcel flag, no prices or barcodes); receipts get the full itemized breakdown, tax, and payment method.

- Full order lifecycle with **Stripe and Cash on Delivery**. Idempotency keys prevent duplicate orders and payments even under retries or network failures.
- Stripe webhooks with signature validation — `payment_intent.succeeded` and `payment_intent.payment_failed` update order status **atomically**, safe against Stripe retries.
- **Cloudinary image rollback** — new images are uploaded first. If the DB write fails, newly uploaded files are deleted and original URLs restored. No orphaned files, no inconsistency.
- Async transactional email via **BullMQ** — all emails queued and processed by a dedicated worker with exponential backoff retry. The API never waits on email delivery.
- **Refresh token rotation** — every refresh invalidates the previous token. Reuse of an old token triggers immediate full session revocation.
- **Full CI/CD pipeline** — GitHub Actions runs the complete Jest + Supertest suite against a dedicated test database on every push to `main`. Deployment blocked on any test failure.

**Application layer**
- **Multi-tenant architecture** — agency-scoped data isolation, per-tenant RBAC, soft deletes with full recovery, and audit logging on every critical mutation.
- **Auth system** — JWT + OTP two-factor, trusted device fingerprinting, session invalidation, office-hours enforcement, and forced password rotation.
- **Provider-agnostic file storage** — a facade layer decoupling every service from the underlying storage provider. Migrated the entire app from Cloudinary to AWS S3 by changing a single import line, with zero changes to business logic across 15+ modules. Temp-upload → permanent-move pattern with atomic rollback on DB failure.
- **Background job pipelines** — BullMQ queues with retry, exponential backoff, idempotency keys, and dead-letter handling via Redis.
- **Real-time messaging** — Socket.IO with room-based agency isolation. Webhook ingestion from Meta Graph API delivers messages to connected clients instantly.
- **Meta Graph API integration** — Facebook and Instagram page management, post publishing (text, image, multi-image, video), conversation sync, and live inbox with webhook-driven updates.

**Infrastructure & DevOps**
- **Provisioned and hardened AWS EC2** from scratch — Ubuntu server, security groups, SSH key management, and an Elastic IP attached up front so instance-type changes never require a DNS update.
- **Nginx reverse proxy** in front of the app, configured for WebSocket pass-through (Socket.IO) and tuned request-size/timeout limits after diagnosing a silent upload failure caused by default proxy limits, not application code.
- **PM2 process management** with boot-persistent auto-start and a memory-restart safety net, so the process self-heals before a leak can take down the whole instance.
- **GitHub Actions CI/CD** with health-check-gated automatic rollback — a failed post-deploy health check reverts to the last known-good commit with no manual intervention, so a bad deploy degrades to "nothing shipped," never to downtime.
- **Diagnosed and fixed a storage-layer bug that looked like an AWS permissions issue but wasn't** — a URL/key mismatch caused S3 to return `403` instead of a clean `404` for missing objects, traced by comparing the stored key against the returned URL rather than re-auditing IAM policy.

## How I think about backend

| | |
|---|---|
| **Failure first** | What happens when step 2 fails after step 1 succeeds? That's the first question I ask. |
| **Concurrency** | Two users, same resource, same millisecond — race condition? I design around it before it ships. |
| **Idempotency** | If this job runs twice, is the result the same? Background jobs must be safe to retry. |
| **Observability** | Structured logs, audit trails, enough context to debug at 2am without reading every line. |
| **Simplicity** | The boring solution that works beats the clever one that breaks under edge cases. |
| **Infrastructure is not someone else's job** | If I ship the feature, I understand what it runs on — the server, the proxy, the process manager, all of it. |
| **Shipped & tested** | CI/CD and tests before calling anything done. I don't push untested code. |
